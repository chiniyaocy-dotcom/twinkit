# 我们怎么衡量这个项目（诚实的指标）

TwinKit 发布后 3 个月的目标：**500+ Star、20+ 真实用户持续使用、5 个以上真实人格包、一份证明“像本人”可以量化的评测报告。** 下面是每个数字的定义，以及我们不会做的事。

## 不做的事

- 不买 Star、不互刷 Star、不用抽奖或奖励换 Star，不让机器人账号点 Star。这些都违反 GitHub 的使用条款，而且会让数字失去意义。
- 不把维护者自己的调用、演示分身的调用、CI 和监控的调用算作“用户”。
- 不挑选对我们有利的评测结果：评测协议预先登记，结果无论好坏都公开。

## 1. Stars

- **定义**：仓库的 `stargazers_count`。
- **统计**：`gallery.yml` 每周一自动记录到 [`gallery/history.csv`](../gallery/history.csv)。

## 2. 真实用户持续使用（目标 ≥ 20）

“用户”是一个真实的人（以 GitHub 账号区分），满足下面任意一条：

| 来源 | 条件 |
|---|---|
| A. 自己部署分身的人 | 在 Gallery 登记了本人的分身（非演示），开启了公开统计，且**近 28 天内至少 8 天**有工具调用 |
| B. 使用分身的人（包括使用别人的分身） | 在每月的 “使用打卡” Discussion 里回复，并且**连续 2 个月**都回复 |

“持续使用用户数” = A 和 B 合并去重后的账号数。A 由 `gallery-check --online` 自动统计（`gallery/STATUS.md`）；B 由维护者每月人工统计并在 Discussion 里公开名单（只列 GitHub 用户名）。

局限：活跃天数统计的是“分身被调用的天数”，不能区分是不是同一个人在用，也可能被刻意刷高；所以它只用于本人登记的分身，并以打卡作为补充。

## 3. 真实人格包（目标 ≥ 5）

Gallery 里满足以下全部条件的条目：

- `demo` 不是 `true`，`consent.owner_is_subject` 为 `true`（本人提交本人的分身）；
- 通过 `scripts/gallery-check.mjs` 的格式检查，endpoint 在线并能响应 MCP；
- 人格包通过 `npm run validate`（公开的人格包由 CI 检查；私有人格包由本人提供检查结果）。

## 4. “像本人”可以量化（目标：1 份合并报告）

- 至少 5 个人按 [评测协议](eval-protocol.md) 完成评测：每人 ≥ 20 个任务、≥ 3 位评委（含本人）。
- 发布合并报告（`node eval/analyze.mjs --run … --run …`），包含每个人的结果、按人合并的平均提升和置信区间、评委一致性，以及所有不支持假设的结果。

## 每周复盘

每周一看一次 `gallery/STATUS.md` 和 `history.csv`：Star 的增长来自哪里（GitHub Traffic 的来源页）、哪些分身掉线了、谁卡在了哪一步。数字不达标时，先问“是不是做出了别人真正想用的东西”，而不是“怎么让数字好看”。
